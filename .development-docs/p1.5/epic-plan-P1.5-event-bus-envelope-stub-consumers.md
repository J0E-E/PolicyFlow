# P1.5 — Event bus + envelope + stub consumers — Epic Plan

Source TDD: [./tdd-P1.5-event-bus-envelope-stub-consumers.md](./tdd-P1.5-event-bus-envelope-stub-consumers.md)

> **Review budget:** ~150 changed lines · ~8 non-generated files · one focused commit per epic. Tunable per project. (Migrations, config, and compose edits are mechanical boilerplate and don't count toward the line budget.)

> High-level agile roadmap. Each epic's design specifics are confirmed with stakeholders at epic time (`4-plan-epic`) before any code is written.

This phase is **backend-only** — no UI epics. The user-facing demo shell is P1.6; the
per-record event timeline that reads this phase's `processed_events` is P1.9. Epics are
ordered simplest-first: the frozen contract, then storage, then the publish side, then
the bus, then the consumers, then runtime wiring, then the two real triggers, then
observability, and finally the named acceptance proof. Each epic leaves the mainline
running when merged — the bus simply sits idle until the triggers (Epics 8–9) feed it.

## Epic 3 — Transactional enqueue — **COMPLETED**
- **Goal:** Provide the transactional outbox write — an `enqueue_event` that inserts the envelope into the caller's tenant `outbox` on the request session, inside the request transaction, so an event is never lost relative to the committed state that produced it.
- **Rough scope:** A small enqueue helper in the events package, with a DB test proving the row is present on commit and gone on rollback, plus per-tenant isolation (tenant A's role cannot read B's outbox).
- **Open questions / decisions for stakeholders:** none expected.
- **Depends on:** Epic 2.
- **Implementation notes:**
  - Added `core/app/events/outbox.py` — `async def enqueue_event(db, envelope)`: maps the envelope 1:1 onto `OutboxEvent` and inserts with a single `db.add(...)` + `await db.flush()` (the `create_record` idiom). Runs on the caller's request session; does **not** commit (the request transaction owns commit/rollback); `published_at` left NULL for the Epic 5 relay. Schema-less `OutboxEvent` resolves into the caller's tenant schema via the active `search_path`, so no schema interpolation.
  - Added `core/tests/test_outbox_enqueue.py` — 4 DB substrate tests (`database_engine`, `@pytest.mark.asyncio`): Phase 1 present-after-commit / absent-after-rollback; Phase 2 lands-only-in-caller-schema / tenant-role-denied-other-outbox. Enqueue runs under the real INSERT-only tenant role (`SET LOCAL ROLE` + `SET LOCAL search_path`); read-back uses the SELECT-capable superuser engine connection, schema-qualified (the tenant role is INSERT-only on its own outbox).
  - **Deviation from the plan's helper snippet (necessary, and the plan's own decision 1 anticipated it):** the helper also sets `occurred_at=envelope.occurred_at` client-side. With it left unset, SQLAlchemy emitted `INSERT ... RETURNING outbox.occurred_at` to fetch the model's `server_default=now()` — which the INSERT-only tenant role cannot SELECT, so the first run raised `permission denied for table outbox`. Setting `occurred_at` from the envelope removes the server-default round-trip (plain INSERT, no `RETURNING`) and is the faithful mapping (the committed event carries the envelope's stamped time). The present-after-commit test asserts `occurred_at` round-trips.
  - Targeted run (per `0-conventions.md` → Targeted test runs), from `core/`: `./.venv/Scripts/python.exe -m pytest tests/test_outbox_enqueue.py -q` → **4 passed**. Backend-only epic → no frontend tests.

## Epic 4 — Broker topology + publish — **COMPLETED**
- **Goal:** Declare the RabbitMQ topology (one durable topic exchange, per-consumer durable queues, per-queue DLX→DLQ with the documented bindings) and publish an envelope to it with the AMQP properties the contract specifies (persistent, `message_id`/`correlation_id`/`tenant_id`).
- **Rough scope:** A broker module under the events package; a unit test asserting the declared bindings as data; the first RabbitMQ testcontainer test that a published envelope lands in its bound queues (adds the `testcontainers[rabbitmq]` dev dependency).
- **Open questions / decisions for stakeholders:** Confirm the aio-pika connection/channel lifecycle (single shared connection vs per-task channel) — settle at epic time; the rest is frozen in the TDD.
- **Depends on:** Epic 1.
- **Implementation notes:**
  - **Connection/channel lifecycle settled: one shared connection, one channel per task.** Recorded as the contract; `broker.py` itself stays lifecycle-agnostic — both `declare_topology` and `publish_envelope` take a `channel` arg and open no connections, so Epics 5–7 own the connection. The Phase 2 test's `broker_channel` fixture realizes one-connection/one-channel and closes both on teardown.
  - **Topology derived from `catalog.CONSUMER_BINDINGS`, not re-listed.** `TOPOLOGY` is a comprehension over the registry (`queue = binding.name`, `routing_keys = binding.routing_keys`, `dead_letter_queue = f"{binding.name}.dlq"`), so queue names / routing keys can never drift from the catalog. Exchange names (`policyflow.events`, `policyflow.events.dlx`) are the only verbatim TDD §5.4 literals.
  - **DLQ bound to the DLX on the same routing keys as the main queue.** Beyond the plan's bullet list, `declare_topology` also binds each `<name>.dlq` to the dead-letter exchange on the queue's routing keys, so a nack-without-requeue (Epic 6) actually routes into the DLQ rather than vanishing. No change to the plan's data shape — just the bind the topic DLX needs to deliver.
  - **Test substrate mirrors the Postgres precedent.** `RABBITMQ_IMAGE = "rabbitmq:3.13-management-alpine"` (pinned to docker-compose / prod), a session-scoped lazy `rabbitmq_container` fixture (no skip logic — "fail always when Docker is absent"), and a `build_amqp_url` helper, all shaped exactly like `postgres_container` / `build_postgresql_url`. Reusable by Epics 5/6/11 so no second broker is booted.
  - **Phase 1 test is an independent hand-transcription** of TDD §5.4 (exchange names + queue→keys/DLQ map), matching `test_event_catalog.py` — a real cross-check, not a tautology over `broker.py`.
  - `testcontainers[rabbitmq]==4.14.2` added to `requirements-dev.txt` (matches the pinned `[postgres]` version; pulls the sync `pika` client for the container readiness probe only — runtime `requirements.txt` untouched). Pre-existing testcontainers `@wait_container_is_ready` DeprecationWarning surfaces from the library, not our code.
  - **Named the topology shape `QueueTopology` (frozen dataclass: `queue` / `routing_keys` / `dead_letter_queue`).** A small added type the plan didn't name explicitly — `TOPOLOGY` is a tuple of these, and the Phase 1 test reads its fields, so it doubles as the data contract Epics 5/6 read.
  - **`publish_envelope` looks the exchange up with `get_exchange`, it does not re-declare it** — so a channel must have had `declare_topology` called on it (or another channel on a connection that did) before the first publish. Caveat for the Epic 7 lifespan ordering: declare topology on startup before any task publishes. The publish channel uses **publisher confirms by default** (aio-pika), so each `publish_envelope` await resolves only once the broker has routed the message — the live test asserts fan-out with no sleeps and Epic 5's relay can mark `published_at` on that same guarantee.
  - **Targeted tests green:** `tests/test_broker_topology.py` 3 passed (no Docker); `tests/test_broker_publish.py` 2 passed (RabbitMQ testcontainer) — 5 passed total. Import smoke `import app.events.broker` clean.

## Epic 5 — Polling relay — **COMPLETED**
- **Goal:** Stand up the own-session polling relay (as `outbox_relay`) that sweeps each tenant's unpublished outbox rows, publishes each to the exchange, and marks `published_at` — with at-least-once semantics by design (a crash between publish and mark re-publishes next sweep).
- **Rough scope:** A relay module exposing a single-sweep function and a loop; a DB+broker test that enqueue → sweep lands the message and marks the row published, that only unpublished rows are selected, and that a forced "published-but-not-marked" row re-publishes on the next sweep.
- **Open questions / decisions for stakeholders:** Confirm the default poll interval (TDD suggests ~1s) and whether a sweep batches or drains fully — tuning only.
- **Depends on:** Epic 3, Epic 4.
- **Implementation notes:**
  - **New module `core/app/events/relay.py`** — Phase 1: `publish_pending_once(broker_channel) -> int` loops `registry.TENANTS`, sums the per-tenant published count, returns the total; the private `_sweep_tenant_outbox` opens the relay's **own** session and in one transaction does `SET LOCAL ROLE outbox_relay` + `SET LOCAL search_path TO <tenant.schema_name>`, selects `published_at IS NULL` rows oldest-first (`order_by(occurred_at)`), and for each row **publishes first then marks** `published_at=func.now()`, committing once at the end. Phase 2: `run_relay_loop(broker_channel, poll_interval_seconds=DEFAULT_POLL_INTERVAL_SECONDS)` — `while True`: sweep, sleep, repeat, with each sweep wrapped in try/except that logs and continues so a transient failure never kills the relay.
  - **Own-session module-global `session_factory`** (imported from `app.db`, **monkeypatched in tests**), mirroring `audit/service.py`; the relay is not on any request path. The role/schema identifiers are fixed registry constants (`OUTBOX_RELAY_ROLE`, `tenant.schema_name`), never user input, so the `SET LOCAL ROLE` / `search_path` interpolation is the safe `audit/service.py` idiom.
  - **Per-tenant single transaction per sweep; publish-before-mark; at-least-once via `published_at IS NULL` keying; `func.now()` server-side mark.** Because `publish_envelope` awaits publisher confirms, a row is marked only after the broker has accepted its message — a crash mid-sweep simply re-publishes the unmarked rows next sweep. The `outbox_relay` SELECT+UPDATE grant is exactly what this needs (no INSERT/DELETE). Each tenant is swept in its own transaction, so one tenant's failure never rolls back another's marks.
  - **`_row_to_envelope(row)`** rebuilds an `EventEnvelope` from the outbox columns 1:1 — the exact reverse of Epic 3's `enqueue_event` envelope→row mapping (wire == dataclass == outbox columns holds in both directions). The relay-only `published_at` marker is not an envelope field, so it is dropped.
  - **Tuning decisions (the epic's two "tuning only" open questions — TDD defaults):** poll interval **~1s** as the named constant `DEFAULT_POLL_INTERVAL_SECONDS = 1.0` (Epic 10 later sources the real value from config `OUTBOX_POLL_INTERVAL_SECONDS` and passes it in); **drain fully** — each sweep selects *all* rows pending at sweep start with no `LIMIT` (simplest; volumes are tiny; batching is a later optimization).
  - **Lifecycle caveat (for Epic 7):** the relay's channel must have had `declare_topology` called on it (or another channel of the same connection) before the first sweep publishes — `publish_envelope` uses `get_exchange`, not declare. Epic 7's lifespan owns that ordering (declare topology on startup before starting the relay task); the tests declare topology in the test body.
  - **Tests `core/tests/test_relay.py` (5 tests).** Phase 1 (DB + broker substrate, `@pytest.mark.asyncio`): enqueue → sweep publishes to **both** bound queues (`enrichment.stub` + `sync.logger` fan-out), round-trips back to the same envelope, and marks the row (`published_at` set, count 1); a second immediate sweep publishes nothing (count 0, queues empty); a row forced back to `published_at = NULL` re-publishes next sweep (count 1 — at-least-once). The relay's own-session global is pointed at the container DB by a per-file `container_relay_session_factory` monkeypatch fixture, mirroring `container_audit_session_factory`; enqueue runs under the real INSERT-only tenant role; read-backs use the SELECT-capable superuser engine connection, schema-qualified. Phase 2 (pure unit, no DB/broker): `run_relay_loop` driven with a counting/flaky stub for `publish_pending_once` — asserts it sweeps at least once, swallows a sweep that raises (survives to the next iteration), and cancels cleanly.
  - **Targeted run** (per `0-conventions.md` → Targeted test runs), from `core/`: `./.venv/Scripts/python.exe -m pytest tests/test_relay.py -q` → **5 passed** (3 DB+broker testcontainer + 2 unit). The lone warning is the pre-existing testcontainers `@wait_container_is_ready` DeprecationWarning from the library, not our code (already noted in Epic 4). Import smoke `import app.events.relay` clean (needs `DATABASE_URL` set for the eager engine, as conftest defaults).
  - **No diagram** (linear sweep flow; the TDD §5 flow diagram already covers the relay segment — offer skipped, matching Epics 1–4).
  - **No deviations** from the plan or Rough scope; no ambiguity required guessing. The one minor addition the plan did not name explicitly: a small `drain_queue_message` test helper (a `queue.get(no_ack=True, fail=False)` read-back) so a later sweep's assertions start from empty queues. Backend-only epic → no frontend tests.

## Epic 6 — Idempotent stub consumers — **COMPLETED**
- **Goal:** Add the two terminal stub handlers (enrichment, sync-logger) that dedupe on `(consumer_name, event_id)` via `processed_events` (own session, `event_consumer`, routed by `tenant_id`), run a canned effect + structured non-PII log, ack on success, and nack-without-requeue to the DLQ on error.
- **Rough scope:** A consumers module under the events package; tests that a consume writes exactly one `processed_events` row, that redelivery of the same `event_id` is idempotent (still one effect), and that a poison message dead-letters.
- **Open questions / decisions for stakeholders:** Confirm the canned-effect shape (what the enrichment stub "returns"/logs) so it stays recognizably non-PII — minor.
- **Depends on:** Epic 2, Epic 4.
- **Implementation notes:**
  - **Canned-effect shape CONFIRMED with the stakeholder: structured metadata only.** Each canned effect is one INFO log carrying a fixed effect label + envelope **metadata only** — `consumer_name`, `event_id`, `event_type`, `tenant_id`, `correlation_id`; the enrichment effect also logs the payload's `entity_type` / `entity_id` reference. **No raw payload dump** → non-PII by construction, and the `correlation_id` seeds the future trace view (P1.9). The stubs stay **terminal** (Decision 8) — record, log, ack; no completion event published.
  - **New module `core/app/events/consumers.py`** (mirrors `relay.py`'s shape). `handle_enrichment(message)` / `handle_sync_logger(message)` are the two frozen handler entrypoints (TDD §5.3), each a thin wrapper over a shared `_consume(message, consumer_name, run_effect)` core: parse the body (`from_message_body`) → record the dedupe row → run the canned effect **only when the row is fresh** (idempotent skip on a duplicate) → `await message.ack()`. `_run_enrichment_effect` / `_run_sync_logger_effect` are the two structured-metadata effects.
  - **`_record_processed_event(consumer_name, envelope) -> bool`** — own session (module-global `session_factory` imported from `app.db`, monkeypatched in tests, mirroring `audit/service.py` / `relay.py`). In one transaction: `SET LOCAL ROLE event_consumer` + `SET LOCAL search_path TO <schema>`, then a Core `postgresql.insert(ProcessedEvent)…on_conflict_do_nothing(index_elements=["consumer_name", "event_id"])`. `id` set client-side (`uuid.uuid4()`), `processed_at` omitted (server default `now()`). Returns whether a row was actually inserted (fresh) vs. a conflict (already processed) via `result.rowcount == 1` — `rowcount` is 1 on insert, 0 on the conflict skip. The Core `insert` emits no implicit `RETURNING` (sidesteps Epic 3's INSERT-only-role `RETURNING` gotcha); `event_consumer` also holds SELECT, so it is double-safe.
  - **`_get_tenant_schema(tenant_id)` + `UnknownEventTenant(LookupError)`** mirror `audit/service.py`'s `_get_audit_schema` / `UnknownAuditTenant`: read `platform.tenants` **as the login role** (before any role switch, so the shared schema is visible), whitelist-validate via `is_known_schema`, raise loud on an unknown tenant. Role + schema are a fixed registry constant and a whitelisted name, so the `SET LOCAL` interpolation is the safe `relay.py` / `audit/service.py` idiom.
  - **Failure path (Phase 2):** the `_consume` core body is wrapped in `try/except Exception` → `logger.exception(...)` + `await message.nack(requeue=False)`, **no re-raise** (the message is terminally handled by dead-lettering; re-raising would confuse aio-pika's already-processed tracking). Both an unparseable body and an `UnknownEventTenant` route to the DLQ. The success and idempotent-duplicate paths still ack.
  - **`__init__.py` untouched** — `consumers.py` is imported by full path (like `relay` / `broker` / `outbox`), so the events package re-exports nothing new.
  - **Tests `core/tests/test_consumers.py` (3 tests, DB + broker substrate, `@pytest.mark.asyncio`).** Added a `container_consumers_session_factory` monkeypatch fixture (mirror of `container_relay_session_factory`). Phase 1: seed + read a real `SUNSHINE` tenant UUID, `declare_topology`, `publish_envelope`, `queue.get(no_ack=False)` the delivered message, call `handle_enrichment` — one consume writes exactly one `processed_events` row (read-back via the SELECT-capable superuser engine connection, schema-qualified — the `test_relay.py` reader idiom); a second delivery of the same `event_id` keeps it at one row and the effect (spied via `monkeypatch`) ran exactly once. Phase 2: publish a malformed-JSON body to `EVENT_EXCHANGE` on `record.created`, deliver it off `enrichment.stub`, call `handle_enrichment` (parse fails → `nack(requeue=False)`), then assert the message lands in `enrichment.stub.dlq` via a short bounded `dlq.get(no_ack=True, fail=False)` poll loop (dead-lettering is broker-side async, not covered by publisher confirms).
  - **Both Phase 1 tests also request `container_keys_session_factory`** (beyond the plan's fixture list): `seed()` encrypts the demo PII rows and so resolves per-tenant keys through `app.pii.keys.session_factory`, which must point at the container too — the same wiring `test_audit_service.py` documents. Without it `seed()` hits the unreachable eager default engine (surfaced as a `127.0.0.1:5432` connect failure on the first run).
  - **Targeted run** (per `0-conventions.md` → Targeted test runs), from `core/`: `./.venv/Scripts/python.exe -m pytest tests/test_consumers.py -q` → **3 passed** (2 Phase 1 DB+broker + 1 Phase 2 DB+broker). Import smoke `import app.events.consumers` clean (needs `DATABASE_URL` set for the eager engine, as conftest defaults). The lone warning is the pre-existing testcontainers `@wait_container_is_ready` DeprecationWarning from the library, not our code (already noted in Epics 4/5). Backend-only epic → no frontend tests.
  - **Size note:** the diff is ~548 lines across 2 files (above the ~150-line budget), but it is a **single focused concern** (the two stub consumers + their tests) and over half of `consumers.py` is docstrings matching the deliberately high docstring density of `relay.py` / `audit/service.py` (the CLAUDE.md house style); the executable logic is small. Kept whole per the `0-conventions` size rule (split only when *materially over AND more than one concern*).

## Epic 7 — Lifespan wiring — **COMPLETED**
- **Goal:** Wire the runtime — a `main.py` lifespan that on startup connects the broker (bounded retry so a boot-order race can't crash core), declares the topology, and starts the relay task plus one consumer task per stub, and on shutdown cancels the tasks and closes the connection cleanly.
- **Rough scope:** Add a lifespan to the core app (which currently has none) and a smoke test that startup/shutdown wire without error. Because the test client's ASGITransport doesn't fire lifespan, tests keep driving the relay/consumers explicitly — the lifespan is the production path only.
- **Open questions / decisions for stakeholders:** Confirm the bounded-retry parameters (attempts/backoff) for an unready broker at boot.
- **Depends on:** Epic 5, Epic 6.
